# 技术说明

面向想了解或修改代码的人。只使用软件的话看 [README](../README.md) 就够了。

## 1. 技术栈

### 前端

- **TypeScript**：前端类型安全和业务逻辑
- **Vite**：开发服务器与生产构建
- **原生 DOM + CSS**：没有引入 UI 框架，便于维护和打包
- **Leaflet**：渲染 OpenStreetMap 瓦片，提供缩放、拖动和图钉
- **高德地图 JS API 2.0**：运行时从高德官方地址加载，需要 Web端(JS API) 类型的 Key 和安全密钥
- **Tauri JavaScript API**：前端调用 Rust command、打开系统文件选择器

### 桌面容器

- **Tauri 2**：Windows 桌面窗口、权限和前后端通信
- **WebView2**：Windows 原生 WebView，运行前端页面

### 后端

- **Rust**：文件分类、备份和外部工具调用（坐标系换算在前端完成）
- **tauri-plugin-dialog**：调用 Windows 原生文件选择器
- **tauri-plugin-fs**：文件系统能力扩展
- **serde / serde_json**：前后端参数序列化

### 元数据处理

- **ExifTool**（官网 Windows 包，13.64）：写入 JPEG、PNG、TIFF、HEIC、RAW 的 EXIF GPS
- **XMP sidecar**：视频使用同名 `.xmp` 文件记录 GPS，避免重新封装和损坏原视频

## 3. 前端代码流程

### 3.1 文件导入

`src/main.ts` 里有三条导入路径，桌面模式下最终都进入 `addPaths()`，交给 Rust 的 `classify_files` 分类（已在列表里的文件会自动跳过）：

- “添加照片、RAW 或视频”按钮：Tauri 原生文件选择器（`openDialog({ multiple: true, ... })`）
- 拖拽：把文件或文件夹拖到左侧“待处理文件”区
- 浏览器预览模式：`input[type=file]`

拖拽由 Tauri 接管，网页收不到普通的 dragover/drop 事件，要用 `getCurrentWebview().onDragDropEvent`：

```ts
getCurrentWebview().onDragDropEvent(event => {
  const payload = event.payload;            // enter / over / drop / leave
  if (payload.type === 'leave') return /* 取消高亮 */;
  // 落点是相对窗口的物理像素，要除以缩放比例才是页面坐标
  const scale = window.devicePixelRatio || 1;
  const inside = overZone(payload.position.x / scale, payload.position.y / scale);
  if (payload.type !== 'drop') return /* 按是否在区域内切换高亮 */;
  if (inside) void addPaths(payload.paths);
});
```

落在左侧区域才导入，落在地图上只提示“请把文件拖到左侧”。Rust 的 `classify_files` 收到文件夹路径时，列出其中直接存放的文件并按文件名排序（不递归）。

桌面模式保存完整文件路径，后续 Rust 才能真正修改原文件。浏览器模式只能进行界面预览。

### 3.2 文件分类

Rust 后端通过文件扩展名区分：

```rust
if raw.contains(&ext.as_str()) {
    "RAW"
} else if video.contains(&ext.as_str()) {
    "视频"
} else {
    "照片"
}
```

真实的 RAW 内容解析和 EXIF 读写交给 ExifTool，而不是自行解析 CR3、NEF 等复杂容器。

### 3.3 位置选择

前端维护：

```ts
let position: LngLat | null = null; // WGS84，没有选点时为 null
```

地图点击、拖动图钉、搜索地点或坐标输入会更新 `position`。没有选点或没有勾选文件时点“写入”会被拦截并提示原因。

两种地图的坐标系不同：OpenStreetMap 是 WGS84，高德是 GCJ-02。程序内部始终保存 WGS84，显示到地图上或从地图取点时用 `src/gcj02.ts` 换算；输入框里的 `纬度,经度` 按当前地图的坐标系解析。切换地图时，视野和图钉保持指向同一个地点。

高德地图在“设置”里填写 Key 和安全密钥后启用。Key 必须是高德开放平台上 **Web端(JS API)** 类型的（Web服务 类型的 Key 不能用于 JS 地图），密钥是同一页面上显示的安全密钥。两者保存在本机 WebView 的 localStorage 中，随 `data` 文件夹走。高德返回 Key 或密钥有误时，地图上会直接显示错误码。

搜索框（回车或点“搜索”按钮）先判断输入是不是坐标：

- `纬度,经度` 直接定位，全角逗号、空格分隔都可以
- 第一个数的绝对值大于 90 时按 `经度,纬度` 处理：国内地图的坐标拾取器复制出来是这个顺序，而纬度不可能超过 90
- 两个数都可能是纬度时，按输入框提示的 `纬度,经度` 解析

不是坐标就当作地点名去搜：

- 配置了高德 Key：用高德的 `AMap.PlaceSearch`，返回 GCJ-02 坐标，定位前换算成 WGS84
- 没配高德 Key：请求 OpenStreetMap 的搜索服务（Nominatim），返回 WGS84 坐标，国内通常需要代理才能连上

搜索结果以下拉列表显示，点一条即定位到该地点并放大到 15 级。地图、搜索和城市查询都需要联网；离线时仍然可以输入坐标。

### 3.4 写入调用

写入只有一个入口。点击“写入 N 个文件”先弹出确认清单，列出写入位置（WGS84 和当前地图坐标）以及每个文件将发生的改动：照片/RAW 是写入 EXIF GPS 并备份为 `xxx.bak`（选了不备份则以红色标出），视频是生成 `xxx.xmp` 且原视频不改动。点“确认写入”后前端才调用 Rust：

```ts
await invoke('write_gps', {
  request: {
    paths,
    latitude: position.lat,   // WGS84
    longitude: position.lon,
    backup: 'sibling'         // 'sibling' 先备份为 .bak，'none' 不备份
  }
})
```

Rust 命令是 async 的，写入在后台执行，界面不会卡住。每个文件的结果直接显示在列表的状态里，失败的写明原因，鼠标悬停可看全文。成功的文件同时在文件名右侧标上“已处理”。

写入结束后，这批文件的结果会记入处理记录（见 3.5）。

Rust 返回逐文件结果，包括：

- 文件路径
- 是否成功
- 写入动作
- 错误信息

### 3.5 处理记录

每次确认写入之后（无论成功还是失败），前端为这批文件各生成一条记录，调用 `record_history` 追加到数据目录下的 `history.jsonl`（每行一个 JSON）：

```json
{"time":"2026/11/26 14:20:31","file":"DSC07369.JPG","path":"D:\\照片\\DSC07369.JPG","status":"成功","latitude":25.6065,"longitude":100.2676,"city":"云南省 大理白族自治州 大理市","error":null}
```

城市用高德的逆地理编码（`AMap.Geocoder`）按写入位置查询，一批文件只查一次；没配高德 Key、查询失败或 4 秒内没返回时留空。

点右上角“处理记录”调用 `load_history` 读回，最新的排在前面。界面有文件名、状态、写入的 GPS、城市四列，失败的记录在下一行写明原因。记录文件只追加、不自动清理，一次最多读回 5000 条；写到一半的残缺行会被跳过，不影响其它记录。

## 4. Rust 后端写入流程

入口位于 `src-tauri/src/lib.rs`，核心步骤：

```text
接收文件路径和目标坐标（WGS84，前端已换算）
        ↓
判断照片/RAW 或视频
        ↓
照片/RAW：创建 .bak（已有则不覆盖；创建失败则这个文件不再写入）
视频：不复制、不改原视频
        ↓
照片/RAW：一次调用 exiftool.exe 写入整批文件的 EXIF GPS
视频：写入同名 .xmp
        ↓
照片/RAW：再调用一次 exiftool.exe 读回 GPS，逐个与指定坐标核对
（没写入且原文件未改动时，删除本次创建的 .bak）
        ↓
返回逐文件成功/失败结果（前端随后把这批结果追加到 data\history.jsonl）
```

### 4.1 ExifTool 调用

ExifTool 来自官网的 Windows 包：`exiftool.exe` 是一个很小的启动器，需要同目录下有 `exiftool_files` 文件夹（ExifTool 本体和 Perl 运行环境）。程序优先查找自身目录下的 `exiftool.exe`，其次才是当前工作目录。

参数不直接放在命令行上，而是写进一个 UTF-8 编码的临时参数文件，用 `-@` 交给 ExifTool。参数文件每行一个参数：

```text
-charset
filename=UTF8
-overwrite_original
-GPSLatitude=25.60650000
-GPSLatitudeRef=N
-GPSLongitude=100.26760000
-GPSLongitudeRef=E
D:\照片\image.CR3
```

这样做是为了支持任意文件名：命令行参数会按系统代码页转换，文件名里的表情符号、部分特殊字母会导致找不到文件。GPS 写在标准的 EXIF GPS 字段里。

一批文件只调用两次 ExifTool：一次写入全部照片，一次把它们的 GPS 读回来。每个文件都以“读回的坐标与指定值一致”为准判定成功。没写入的算失败，并给出 ExifTool 对这个文件报的错（例如 `Not a valid JPG`）；找不到 `exiftool.exe` 时返回明确错误，不会假装写入。

实测速度：30 张 7 MB 的 JPEG（含备份）约 2 秒，每张不到 0.1 秒；文件很大时主要耗在复制和重写文件本身。写入期间界面可以正常操作，但列表只显示“写入中…”，没有逐个进度。

用实际文件验证过的格式：Sony ARW（A7 II、A7 IV）、JPEG、iPhone HEIC、PNG、TIFF。

### 4.2 RAW 支持策略

RAW 文件不进行解码、重渲染或重新编码。程序只让 ExifTool 修改元数据区域：

- CR2 / CR3：Canon RAW
- NEF：Nikon RAW
- ARW：Sony RAW
- DNG：Adobe/通用 RAW
- RAF：Fujifilm RAW
- ORF：Olympus RAW
- RW2：Panasonic RAW
- PEF：Pentax RAW
- SRW：Samsung RAW

写入前创建 `.bak`，这样即使用户不满意，也能恢复原文件。

### 4.3 视频策略

视频默认不原地修改容器，也不重新编码。程序创建：

```text
视频文件.mp4.xmp
```

XMP 中记录：

- GPSLatitude
- GPSLongitude
- 纬度方向
- 经度方向

这样不会影响视频画质，也避免重封装失败。

## 5. 坐标系设计

### WGS84

- GPS 和 EXIF 的通用标准
- OpenStreetMap 使用的坐标系
- 程序内部保存、最终写入 EXIF 的坐标系

### GCJ-02

- 高德等国内地图使用的“火星坐标系”，与 WGS84 相差约 300～1000 米
- 仅在中国大陆范围内进行转换
- 显示到高德地图时由 WGS84 换算得到，从高德地图取点时换算回 WGS84

换算在 `src/gcj02.ts` 中实现：

```ts
wgs84ToGcj02(lat, lon)
gcj02ToWgs84(lat, lon)
```

逆变换用迭代求逆，与公开的参考点一致，往返误差小于 1e-9 度。海外坐标不套用偏移。程序目前不涉及 BD-09（百度）。

## 6. 数据存放

绿色版的数据默认放在 exe 同目录的 `data` 文件夹，该目录不可写时回退到 `%LOCALAPPDATA%\com.photogps.manager`。里面有：

- `EBWebView\`：WebView2 的用户数据，其中 localStorage 保存着高德 Key、安全密钥和上次用的地图
- `history.jsonl`：处理记录，只追加
